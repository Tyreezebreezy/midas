## What's in this release

A private, local-first personal finance desktop app. Everything in
`v0.1.0` (accounts, manual transactions, staged CSV import, merchant
rules, recurring/bill detection, budgets, pay-cycle tracking, Safe to
Spend, savings goals, net worth, backup/export/restore) plus ten
subsequent development batches: OFX/QFX statement import (1.x and 2.x)
sharing one duplicate-protected pipeline with CSV; account reconciliation
against a real statement with running balances and full history;
transaction intelligence (payees, tags, splits, bulk edits,
correction-to-rule, one-time flagging); Recurring Intelligence
(subscription/bill/income pattern detection, price-change and
missed-occurrence tracking, expected-vs-actual matching); Budget
Intelligence (rollover, spending pace, historical-typical suggestions,
future-month overrides); Insights (Spending/Income/Merchants/Cash
Flow/Net Worth with period-over-period comparison); a deterministic
7/14/30-day cash Forecast; a unified Review Center with a factual Data
Health checklist and six deterministic Financial Signals; first-run
onboarding; and Privacy Mode (a one-click toggle that masks every
displayed dollar amount). See `specs/phase-008-*` through
`specs/phase-018-*` for full per-batch detail.

  clean. Full frontend check (`prettier --check .` clean on source;
  `tsc --noEmit`; `node --test` 17/17; `vite build`) - clean.
- **Fresh install** (disposable Tauri identifier, never touching real
  app-data): installed silently, launched the real installed binary
  (`http://tauri.localhost/`, no dev server), confirmed a brand-new

- **Real v0.1.0 database upgrade** (through the actual application
  startup path, not only unit tests): a genuine v0.1.0-schema database
  built from the repository's own migration files 0001-0007, seeded with
  realistic multi-account data, reached `user_version = 14` cleanly with
  `PRAGMA integrity_check = ok` and zero `foreign_key_check` violations;
  every downstream Batch 1-10 feature computed correctly against the
  migrated data, hand-verified exactly.
- **Backup/restore round trip**: live through the real Settings UI -
  downloaded a real backup (verified via `node:sqlite`: valid, correct
  schema/counts), made a further change, restored via the actual file
  input, reloaded, confirmed exactly the backup-point state returned
  (no hybrid state), the pre-restore safety copy was present on disk, and
  the resulting live database passed both integrity checks.
- **Installer/uninstall/reinstall** (disposable identifier; this exact
  rebuilt binary): fresh install; uninstall left the database SHA-256
  byte-for-byte identical; reinstall after full uninstall returned real
  account data intact with onboarding correctly not re-triggering; a
  silent (`/S`) reinstall directly over an existing installation - the
  historical hang documented in `docs/release/0.1.0.md` - completed
  cleanly within 15 seconds and did **not** reproduce.
- **Import hardening**: OFX/QFX fixture library (date variants, overlap,
  duplicate-FITID, multi-account, malformed, investment-rejection) and a
  live CSV edge-case fixture (reordered/extra columns, quoted commas,
  MM/DD/YYYY dates, a blank required field) both handled correctly; found
  and fixed a raw parser-error leak (`ofx.rs`) and a misleading
  malformed-row preview fallback (`ImportWizard.tsx`).
- **Import stress test**: 5,000 synthetic rows parsed/previewed/committed
  correctly with no data-integrity issue; confirmed and documented (not
  fixed) that the Transactions table has no list virtualization and
  becomes noticeably slower (~2.3s render) at that volume.
- **Concurrency**: a second `midas.exe` launched against the same
  database while the first was running did not corrupt data (SQLite's
  own file locking, not a Tauri-level guard, is what prevents this).
- **Theme/responsive/accessibility/long-content**: light and dark themes

## Known limitations

- **The Transactions table has no list virtualization or pagination.**
  Confirmed via a 5,000-row stress test: everything computes correctly,
  but rendering that many rows takes a few seconds and scrolling gets
  noticeably heavier. Normal day-to-day ledgers (hundreds, not thousands,
  of rows per account) are unaffected; date-range and account filters
  already let you narrow a large ledger. Recommended as a follow-up for a
  future performance-focused batch rather than fixed here, to avoid
  introducing a new UI rendering dependency immediately before release.
- **A database-open failure at launch has no visible in-app feedback.**
  A release build has no console window; if `db::open` ever fails (e.g. a
  genuinely corrupted database file), the app currently just doesn't
  launch, with only a best-effort `launch-error.log` (next to where the
  database would be) as a diagnostic trail - no in-app dialog. The
  underlying safety property (never write to a database it can't read)
  already held before this release; this is a feedback gap, not a
  data-safety one. Not fully fixed here since a proper in-app dialog would
  need a new dependency touching the most startup-critical code path
  immediately before a release candidate.
- Backups are manual, not scheduled or automatic - MIDAS doesn't run in
  the background.
- The database file is not encrypted at rest - relies on OS-level disk/
  account security.
- CSV export is one-way, for reading elsewhere - not intended to
  round-trip back through the importer.
- No multi-device sync - each installation has its own independent
  database unless manually backed up and restored between them.
- Windows is the only platform built and tested.
- Investment/brokerage OFX statements are explicitly rejected (not
  silently misread) - MIDAS does not model securities.
- The historical silent-reinstall-over-existing-install hang
  (`docs/release/0.1.0.md`) was specifically re-tested this release and
  did **not** reproduce - recorded here as resolved, not as a still-open
  limitation, in case a different environment still exhibits it.
