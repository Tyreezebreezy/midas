# Release checklist: MIDAS 1.0.0-rc.2 (toolchain/CI modernization)

- Source commit for this record: pending (this file is written before the

  commit once pushed).
- Owner release gate: modernization work was explicitly pre-authorized

  see "Release state" below.
- Gitea remote: `[private-git-server]`

## What's in this release

A **technical modernization pass, not a feature release**. No financial
feature, navigation, workflow, migration, or visual behavior changed -
see `standards/MODERNIZATION.md`'s baseline contract below for what was
preserved vs. changed. Everything `v1.0.0-rc.1`
(`docs/release/1.0.0-rc.1.md`) already covers still applies unchanged.

### Preserved

Every financial feature, page, migration, and visual/accessibility
behavior verified in `v1.0.0-rc.1`. 460 Rust tests and 17 frontend tests
are unchanged in count and still pass. `v0.1.0` and `v1.0.0-rc.1` remain
untouched, protected rollback baselines.

### Changed

- **Toolchain pinned**: `.node-version` (24.21.0, Node 24 LTS) and
  `rust-toolchain.toml` (1.98.1, minimal profile + clippy/rustfmt) so
  local dev and CI use the identical, reproducible toolchain rather than
  "whatever happens to be installed."
- **Frontend dependencies bumped** (each gated on typecheck/tests/build):
  React/React DOM 19.1.0 -> 19.3.0, `@tauri-apps/cli` 2.11.4 -> 2.11.5,
  Prettier 3.6.2 -> 3.9.8, TypeScript ~5.8.3 -> ^6.0.3, Vite ^7.0.4 ->
  ^8.3.0 together with `@vitejs/plugin-react` ^4.6.0 -> ^6.1.1 (a
  required coherent pair - plugin-react 6 needs Vite 8 as a peer).
  **Deliberately did not adopt TypeScript 7.x**: it is a full rewrite of
  the compiler in Go with no public programmatic compiler API yet
  (Microsoft's own stated plan is a new, different API in a later 7.1),
  so any tooling that imports `typescript` as a library cannot run on it
  without a compatibility shim. 6.0.3 is the last release on the mature,
  structurally-identical JS-codebase compiler. Recorded in
  `.forge/dependencies.json`.
- **One real TypeScript 6 compatibility fix**: `BackupPage.tsx`'s
  `base64ToBytes` returned a bare `Uint8Array`, which newer `lib.dom.d.ts`
  types as `Uint8Array<ArrayBufferLike>` - too wide for `BlobPart`, which
  now requires `Uint8Array<ArrayBuffer>`. Fixed by annotating the actual
  return type (`new Uint8Array(length)` always allocates a real
  `ArrayBuffer`, never `SharedArrayBuffer`); no behavior change.
- **Rust dependencies**: `cargo update` applied 40+ safe transitive
  bumps, all within already-declared semver ranges (`tauri` 2.11.5 ->
  2.11.6, plus transitive crates). No direct `Cargo.toml` version
  constraint changed - `quick-xml` in particular was deliberately held at
  0.41.0 (see `.forge/dependencies.json` for the reasoning: a 0.x -> 0.y
  bump is semver-major for a pre-1.0 crate, and the OFX/QFX parser built
  on it is release-hardened with no defect motivating churn).
- **App-data identity isolation** (the actual point of this pass): the
  base `src-tauri/tauri.conf.json` identifier changed from the real
  `com.breezy.midas` to `com.breezy.midas.dev`. Two small Tauri `--config`
  overlays add the other two identities: `tauri.prod.conf.json`
  (`com.breezy.midas`, used only by the new `npm run package` script) and
  `tauri.test.conf.json` (`com.breezy.midas.test`, used only by
  `npm run tauri:test` / `scripts/smoke.ps1`). `npm run tauri dev` - the
  command a developer runs every day - now resolves to the isolated dev
  identity automatically, with no flag to remember. Live-verified (see
  Test results) with byte-identical production data before and after.
  `.forge/architecture-fitness.json` adds an automated check that the
  base config can never revert to the real identifier.
- **Local verification tooling**: `scripts/verify.ps1` (the canonical
  name for the existing gate, kept as `validate.ps1` too for historical
  continuity), `scripts/release-check.ps1` (clean tree, on `main`, in
  sync with `origin/main`, version consistency, full gate, security
  scans), `scripts/smoke.ps1` + `scripts/smoke-check.mjs` (launches the
  disposable test identity, confirms it over real Tauri IPC, tears down
  and wipes its data automatically).
- **Gitea Actions**: `.gitea/workflows/validate.yml` (gate on every push
  to `main`) and `.gitea/workflows/release.yml` (on a pushed `v*` tag:
  validate version consistency, full gate, security scans, build with
  `npm run package`, hash, write a release manifest, publish a private
  Gitea Release with the installer/checksum/manifest attached and
  `docs/release/<version>.md` as the notes - using only the automatically
  issued per-job token, no manual secret). See "Release state" for what
  is still required before this can actually run.
- **Forge alignment**: adopted `.forge/*` project controls (identity,
  capabilities, toolchain ranges, migrations, dependency governance,
  architecture fitness, evidence) and `docs/forge/*` contracts, brought
  forward and refreshed from the earlier `chore/forge-adoption` field
  test (which never merged and had gone stale - migration 13 vs. the
  current 14, version 0.1.0, evidence citing pre-Batch-10 specs). Forge's
  own Repo Polish, controls, and hardening validators all pass against
  current `main`.

### Fixed

The TypeScript 6 `Uint8Array<ArrayBuffer>` compatibility issue above -
the only source-code change in this pass.

### Removed

Nothing.

## Test results

- **Full gate**: `cargo fmt --check`, `cargo check --locked`,
  `cargo clippy --all-targets --locked -- -D warnings`,
  `cargo test --locked` (460/460, unchanged count), `cargo audit` (same 7
  pre-existing accepted advisories) - all clean. Frontend `tsc --noEmit`,
  `node --test` (17/17, unchanged), `vite build` - all clean under the
  new TypeScript 6 / Vite 8 toolchain.
- **Security**: `npm audit` 0 vulnerabilities; Gitleaks 0 leaks across 83
  commits + working tree; Trivy (vuln+secret, both lockfiles) 0
  critical/high, same 1 pre-existing accepted MEDIUM `glib` advisory
  `cargo audit` already accepts.
- **Production-safety proof** (the mandatory identity-isolation test):
  captured the real production database's SHA-256
  (`81b7558891ebf4e427911e8eec26fbb5fa78fc2311854e701430ee0048c2de91`,
  26 accounts) before touching anything. Launched `npm run tauri dev`
  (bare, no flags) - saw a brand-new, separate database with 0 accounts.
  Launched `npm run tauri:test` via `scripts/smoke.ps1` - same, 0
  accounts, auto-cleaned up afterward. Created one recognizable account
  ("DEV IDENTITY ISOLATION PROOF") in the dev identity. Relaunched with
  the production config overlay - saw the real 26 accounts, not dev's 1
  or test's 0. Re-hashed the production database: identical,
  byte-for-byte, to the value captured before any of this - production
  was never written to at any point in this whole pass.
- **Release-build path**: built the installer via the new
  `npm run package` script (the production `--config` overlay) from a
  clean tree. Confirmed via string search of the compiled `midas.exe`
  that it embeds exactly `com.breezy.midas` and contains zero occurrences
  of `com.breezy.midas.dev`/`.test` - the merge produced the correct,
  real identifier with no leftover dev/test leakage.

## Known limitations

Same as `v1.0.0-rc.1` (Transactions table has no list virtualization at
5,000+ rows; a database-open failure at launch has only a log-file
diagnostic, no in-app dialog) - neither touched by this pass.

**New, from this pass**: the Gitea Actions workflows exist and are
correctly authored but have never actually executed - this Gitea
instance has **zero registered Actions runners** (repo, owner, and
instance-admin level all confirmed empty). Registering a self-hosted
Windows runner is a real, persistent, host-level change (a new
background process/service), so it was deliberately left as an owner
action rather than done autonomously - see "Release state."

## Release state

- **Version bumped** to `1.0.0-rc.2` across `package.json`,
  `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`, and
  `.forge/project.json`. Not yet tagged.
- **A real installer was built locally** to prove the new production
  `--config` path works (`MIDAS_1.0.0-rc.2_x64-setup.exe`, 3,149,636
  bytes, SHA-256
  `aefa6b19076768ebc30a11e2bf11078f0c29b39b5e5c37a8063a2b464d5887ec`) -
  this is a verification build, not a published release artifact.
- **No tag was created and no Gitea Release was published in this
  pass.** Doing so manually again would repeat exactly the problem this
  modernization exists to eliminate. The one remaining step is entirely
  the owner's: register a self-hosted Windows runner (**Settings ->
  Actions -> Runners**, label `self-hosted-windows`) on a host with Node/
  Rust/Tauri-Windows-prerequisites/Gitleaks/Trivy already installed
  (README.md's "Development" section has the full list), then push
  `git tag -a v1.0.0-rc.2 -m "..."` and `git push origin v1.0.0-rc.2` -
  `.gitea/workflows/release.yml` takes it from there and publishes the
  private Gitea Release automatically, with no browser step and no
  Claude-held credential.
