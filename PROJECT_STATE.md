Batch 4 / Account Reconciliation + Running Balances (`specs/phase-011-reconciliation/spec.md`) is complete: a new `reconciliations` table (migration 0011, status `completed`/`needs_review`/`reopened`) plus one nullable `transactions.reconciliation_id` FK let an account's transactions be matched against a real bank/credit-card statement for a period, cleared one by one, and closed once the difference against the statement is exactly zero - all recomputed server-side, never trusted from the frontend. The cleared-balance formula always counts `opening_balance`/`balance_adjustment` (owner-asserted anchors) regardless of clearing state, and everything else only once explicitly `cleared`/`reconciled`; credit cards needed zero special-casing since ADR-0004's existing sign convention already matches the "positive = amount owed" a real statement shows. Reopening reverts transactions to `Cleared` (not `Unreconciled`) and frees the period while keeping the old record in history for audit purposes. Deterministic running balances (`transaction_date ASC, id ASC`, mirroring the existing list ordering's own tie-break) are available in the reconciliation workspace always and on Transactions via an opt-in checkbox scoped to one selected account. Batch 3's OFX parser was found to discard the statement period (`DTSTART`/`DTEND`) entirely - extended to preserve it as a reconciliation prefill hint, never automatic. No bugs found in the reconciliation logic itself during native verification.
