- Phase 4A — Accounting boundary hardening: COMPLETE (2026-08-25). Account balance is now computed live from `SUM(transactions.amount_cents)`, never a separately-maintained column (ADR-0007) - the sign-convention invariant ADR-0004 always described is now actually enforced. A new `opening_balance` transaction type is the single mechanism for both setting a starting balance and reconciling it later (deterministic delta-from-known-balance, auto-anchored before the earliest other transaction, upserted not accumulated). `accounting::spending_effect`/`total_spending`/`net_worth` give Phase 4B a shared, tested foundation. ADR-0006 (hand-rolled dates) reassessed and superseded by ADR-0008 (`chrono::NaiveDate`, one transitive dependency, zero timezone/clock surface) now that Phase 4B's calendar needs exceed simple day-counting; all hand-rolled calendar code deleted rather than kept in parallel. 94 Rust tests (+16 net), every owner-required case live-verified end-to-end. Ponytail-reviewed (one finding applied: two identical-`WHERE`-clause queries in `reconcile_balance` merged into one).
- Phase 4B — Core financial intelligence: COMPLETE (2026-08-26). Budgets (planned vs. actual, transfers excluded, refunds netted, historical comparison against real spending not just prior budgets), Savings Goals (plain fields, computed status, opt-in Safe-to-Spend reservation), Pay Cycle (four schedule shapes, income-pattern detection that only ever proposes, obligations reused everywhere else that needs them), Safe to Spend (the headline number, every line item exposed, an honest incomplete state instead of false precision), and Net Worth (assets/liabilities breakdown plus a 6-month trend recomputed from the ledger, no snapshot table). Credit-card safeguards folded into the accounting boundary and Safe to Spend rather than built as a separate mechanism nothing specified independently. A real bug (an archived account's leftover confirmed recurring series inflating Safe to Spend's obligations) was caught during live verification and fixed with a shared `active_account_series` filter plus a regression test - exactly the kind of cross-feature interaction unit tests alone would never surface. 145 Rust tests (+51 from Phase 4A), all six owner-numbered items live-verified end-to-end with hand-computed arithmetic matching exactly. Ponytail-reviewed at every checkpoint (findings applied: a duplicate date computation, three inline-`style` → CSS-class fixes, a hand-rolled month-name array replaced with native `Intl.DateTimeFormat`).
- Phase 4C — Accounting correction: COMPLETE (2026-08-26). Fixed a real bug in Phase 4A's `reconcile_balance`: every reconciliation after the first rewrote the single `opening_balance` transaction's date as well as its amount, silently altering historical net-worth-as-of-a-past-date calculations. Split into `opening_balance` (anchored once, never touched again) and a new `balance_adjustment` type (dated at its own reconciliation date, at most one per account per date, upserted in place) - ADR-0009 supersedes ADR-0007's mechanism section. `reconcile_balance` is now a two-path dispatcher with the same public signature; zero callers changed. Excluded `balance_adjustment` from `recurring::detect_candidates` (unlike the structurally-capped `opening_balance`, an account reconciled regularly can produce 3+ same-merchant, evenly-spaced rows - exactly what the detector looks for) with a regression test proving it. 153 Rust tests (+8 from Phase 4B). Live-verified against the real app: a real "Update balance" submission produced a separate, correctly-dated adjustment, left the opening balance untouched, and moved balance/net worth/Safe to Spend by exactly the delta while every earlier month's net-worth trend point stayed identical. Ponytail-reviewed (one finding applied: a stale ADR-0007-era doc comment left in place above the new ADR-0009 one, contradicting the code beneath it).
- Phase 5 — Overview and Reports: COMPLETE (2026-08-26).
